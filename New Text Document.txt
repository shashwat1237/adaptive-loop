4. What exactly would you build?









Feature 1 — Protocol-to-outcome timeline

Convert each approved recommendation into a structured protocol with a start date, intended outcome, adherence signals, relevant biomarkers and a review date.

Example: a clinician-approved sleep intervention is tracked against sleep duration, regularity and relevant recovery measures, rather than being represented only as a checklist.












Feature 2 — Change and confounder analysis

Detect meaningful changes in available data and annotate potential confounders such as illness, travel, training load or missing measurements.

The engine should distinguish an observed change from a possible explanation. It must not claim that a supplement or lifestyle intervention caused a biomarker change simply because the two occurred together.












Feature 3 — Evidence-backed next-step recommendations

For each protocol, show what was expected, what was observed, how complete the evidence is and what remains uncertain.

Produce a structured outcome: continue as prescribed, request more data, discuss an adjustment with a clinician, or arrange clinical review when appropriate.












Feature 4 — Six-month review report

Automatically prepare a clinician-reviewable summary of baseline versus follow-up biomarkers, wearable trends, adherence and missing data, along with a clear explanation of what improved, worsened or remains inconclusive.

This directly complements AXO's existing repeat-testing model without replacing its clinical team.

AXO Adaptive Loop — Simple AI-First Architecture
My recommendation is to build Adaptive Loop: an AI system that studies what happens after a person starts a health intervention and proposes what to investigate next.

The important part: AI does the reasoning. Python handles data preparation, calculations and verification. You do not need to write hundreds of healthcare rules or train your own model.

Since you don't have healthcare-domain knowledge, build this as a research and decision-support prototype using synthetic data—not as a system that diagnoses people or independently changes their treatment.
1. The architecture
1. Synthetic Health Data

Biomarker results · Wearable time series · Intervention history · Context notes

2. Python Data Preparation

Pandas cleans and aligns dates, handles missing values and computes basic trends

3. AI Reasoning Engine
Core product
LLM synthesizes trends, adherence, context and competing explanations

Produces hypotheses · Confidence with justification · Missing evidence · Proposed next investigation

4. Evidence Verification

Check claims against source data, verify calculations, flag unsupported conclusions and allow abstention

5. Adaptive Loop Dashboard

What changed? What might explain it? What remains unknown? What should be reviewed next?


This is a single application, not a collection of microservices. You can build the entire prototype with Python, FastAPI, an LLM API, and a React frontend.
2. What each component actually does

Component A — Data simulator

Generate fictional people, biomarker measurements, wearable trends, intervention start dates and adherence records.

You control the synthetic scenarios, so you can test whether the AI notices a known change, missing data or a misleading correlation.




Component B — Data preparation

Use Pandas to organize observations by date and intervention. Calculate simple summaries such as weekly averages, baseline-versus-follow-up differences and data completeness.

This is ordinary data engineering, not a healthcare rule engine. The LLM should receive readable summaries rather than thousands of unprocessed measurements.




Component C — AI analyst

Send the prepared evidence to an LLM, such as a model accessible through Groq.

Ask it to compare trends, generate competing explanations, identify confounders, explain uncertainty and propose the most useful next investigation. Require structured JSON output using Pydantic schemas.

This is where the product's intelligence lives. You define the reasoning task and output format, not every possible conclusion.




Component D — AI critic and evidence checker

A second LLM call reviews the first answer. It checks whether the cited measurements support each claim, whether alternative explanations were considered and whether the conclusion is too strong.

Python separately checks that cited observation IDs exist and numerical calculations match the source data. The critic can reject a conclusion or request abstention.




Component E — Dashboard

Display the original measurements, the AI's hypotheses, evidence supporting each hypothesis, counterarguments, missing data and suggested next steps.

Users should be able to inspect the evidence behind a conclusion instead of trusting a chat response blindly.



3. How the AI reasoning should work
Don't build a multi-agent swarm. Start with two LLM calls per analysis: one analyst and one critic.
INPUT EXAMPLE — FICTIONAL DATA

A person's sleep duration improved from a weekly average of 6.1 hours to 7.0 hours after a new sleep routine. Their wearable recovery score also increased, but their exercise load decreased during the same period.


LLM CALL 1 — ANALYST

The model might identify improved sleep and recovery as observed changes, with reduced exercise load as a competing explanation. It should not automatically attribute the recovery change to the sleep routine.


LLM CALL 2 — CRITIC

The critic checks the original measurements and challenges unsupported claims. If the data cannot distinguish between explanations, it should say so.


OUTPUT — ADAPTIVE LOOP
- Observed: Both sleep duration and recovery score increased.
- Possible explanation: Better sleep may have contributed.
- Alternative: Lower exercise load may also explain the change.
- Unknown: The relative contribution of each factor.
- Next investigation: Review additional comparable weeks and contextual data before drawing a stronger conclusion.


The output above illustrates the intended behavior, not a claim about a real patient.

One important technical point: the model's self-reported confidence is not a calibrated probability. Initially, ask it to provide a qualitative confidence level with a justification and explicit evidence gaps. You can evaluate its reliability against your synthetic test cases later.

6. What not to build yet
- No fine-tuning or training your own ML model.
- No LangGraph or complex multi-agent orchestration.
- No wearable APIs or real patient records.
- No medical knowledge graph or vector database.
- No automated treatment changes or diagnostic claims.
- No hundreds of hand-written clinical rules.
You need ordinary data validation and arithmetic checks, but you do not need to encode the clinical reasoning yourself.
7. Build it in this order
1. Create the synthetic dataset. Include baseline measurements, daily wearable trends, intervention dates, adherence and contextual events.
2. Build the Pandas processor. Return clean, dated summaries with links to the original observations.
3. Build the AI analyst. Have it produce hypotheses, supporting evidence, alternatives, unknowns and proposed investigations in a fixed JSON schema.
4. Add the critic. Test whether it catches fabricated evidence references, unsupported causality and missing context.
5. Build the dashboard. Let a user inspect the timeline and expand each hypothesis to see its evidence and counterarguments.
6. Test failure cases. Give the system incomplete, contradictory and misleading synthetic data. A good system must sometimes say that the evidence is insufficient.
My final recommendation: start with one FastAPI backend, one LLM analyst, one LLM critic and one dashboard. Make the AI reasoning demonstrably useful and falsifiable before adding any additional components.

Your strongest differentiator is not that you used an LLM. It is that Adaptive Loop can explain what changed, explore plausible explanations, show precisely which evidence supports each claim, and recognize when it cannot determine the answer.
